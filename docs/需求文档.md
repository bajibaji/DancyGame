# 需求文档 — 杭州刑侦互动文字游戏

版本：2026-11-22 v1 需求基线。原有技术和移动端约束继续适用；2026-11-23 叙事版的现行剧本与状态规则见[编剧知识库](./编剧知识库.md)和[节奏设计](./节奏设计.md)。下文组件规划、里程碑中的示例文件名不是当前实现清单。

## 1. 项目概述

把小说《空相沙漏[刑侦]》改编为 React 网页文字游戏：悬疑刑侦主题，真实杭州 2015 年地理，主角江嘉（26 岁女刑警、失忆），玩家通过 ABC 三选一推进剧情，线索/关系/危险三值驱动走向好/坏/中立三结局。不接入任何大模型，全部文案与选项预写，纯本地状态机，可离线游玩。

## 2. 核心玩法循环

1. 阅读场景叙事（打字机可跳过）。
2. 每个分支点做 ABC 三选一；选项直接写行动，不显示取向、风险或数值。
3. 选择立即结算，新材料入档；后果写进下一幕。可在下一幕推进前、选择后 5 秒内撤销。
4. 推理板是档案库中的可选功能。组合两张已获得的卡片，正确时 +2 线索，不写入主线真相标记。
5. 终章按三值/记忆/flags 判定结局，展示结局文本与关键分歧回放，最后做去留尾声选择。

硬性玩法约束：
- 每个分支点恰好 3 个选项（A/B/C），全部推进剧情，禁止空转选项。
- 每个选项必须至少产生一项状态变化（三值/记忆/flag/线索），禁止伪选择。
- 选项的取向（直觉/证据/共情）与数值变化由剧情数据固定，同一选项永远同一效果，可复现。
- 高风险选项必须绑定高价值回报；不允许存在严格支配选项（某选项在所有维度不劣于另一项）。
- 三结局必须全部可达；固定策略验证预定路线，固定种子 5000 局抽样验证结局和线索分数覆盖。抽样不代表玩家实际分布。

## 4. 状态模型与存档

```ts
type Tendency = 'intuition' | 'evidence' | 'empathy'
type Risk = 'low' | 'medium' | 'high'
type Phase = 'title' | 'prologue' | 'play' | 'puzzle' | 'finale' | 'ended'
type EndingId = 'good' | 'bad' | 'neutral'

interface Option { key: 'A' | 'B' | 'C'; label: string; tendency: Tendency; risk: Risk; effects: Effects; next: string }
interface Effects { clue?: number; relation?: number; danger?: number; memory?: number; flags?: string[]; clues?: string[]; memories?: string[] }
interface Scene { id: string; chapter: string; title: string; locationId: string; timeOfDay: string; body: string; options: Option[]; ending?: EndingId }

interface GameStore {
  run: { sessionId: string; saveVersion: 1; sceneId: string; chapter: string; phase: Phase; startedAt: number }
  meta: { clue: number; relation: number; danger: number; memory: number }
  relationship: Record<string, number>
  flags: Record<string, boolean | number>
  clues: string[]
  memories: string[]
  history: { sceneId: string; choice: 'A' | 'B' | 'C'; at: number }[]
  snapshot: Snapshot | null
  ending: { id: EndingId; at: number } | null
  actions: {
    startNewRun(): void
    choose(o: Option): void
    undo(): void
    openPuzzle(result: { flag?: string }): void
    settleEnding(): void
  }
}
```

规则：初值 线索 5 / 关系 4 / 危险 2 / 记忆 0；全部 clamp 到声明范围；关系值 7 人独立追踪；结局判定唯一入口 ending.ts。

存档：localStorage key `jiangjia.save.v1`，settings 单独存 `jiangjia.settings.v1`；persist partialize 只存 run/meta/relationship/flags/clues/memories/history/ending；选择前写快照（3-5 秒撤销），撤销回到上一场景并还原全部状态；存档损坏时备份原档、回标题页并提示；版本迁移用 migrate。

## 5. 剧情数据结构

章节文件 src/content/story/ch01.json 等，schema（zod 校验，构建时与测试时各跑一次）：

```json
{
  "chapter": "ch01",
  "title": "凶喜·熏桶",
  "scenes": [
    {
      "id": "ch01-03",
      "chapter": "ch01",
      "title": "八万元",
      "locationId": "hangbo-ban",
      "timeOfDay": "夜",
      "body": "……预写正文 300-600 字……",
      "options": [
        { "key": "A", "label": "连夜去卢旭家堵人，逼她当场亮流水。", "tendency": "intuition", "risk": "high", "effects": { "clue": 2, "relation": -1, "danger": 2, "flags": ["F05_LU_TORN"], "clues": ["C04"] }, "next": "ch01-04" },
        { "key": "B", "label": "依法布控账户，等银行明早出流水。", "tendency": "evidence", "risk": "low", "effects": { "clue": 1, "relation": 1, "danger": -1, "flags": ["F06_ACCOUNT_WATCH"], "clues": ["C04"] }, "next": "ch01-04" },
        { "key": "C", "label": "先找卢旭的母亲，让她劝女儿主动交证。", "tendency": "empathy", "risk": "low", "effects": { "clue": 1, "relation": 1, "flags": ["F07_LU_FAMILY"], "clues": ["C04"] }, "next": "ch01-04" }
      ]
    }
  ]
}
```

数据硬性规则（story-data.test.ts 校验）：
- 场景 id 全局唯一；每个非结局场景恰好 3 个选项且 key 依次 A/B/C；选项 next 必须指向存在的场景。
- 从起点场景图可达全部场景；无孤立场景。
- 结局场景 ending 字段 ∈ good/bad/neutral，且三类结局各至少一个可达。
- tendency ∈ 三取向枚举；同一分支点三选项不得全同取向。
- effects 数值 |Δ|≤3 且落在三值范围内。
- 线索 id 必须在 clues.json 中存在；地点 id 必须在 hz-locations.json 中存在。
- flags 写入集合与读取集合一致，无死 flag（写入必须至少被结局判定或场景条件读取）。
- body 不含占位符、内部 id、开发残留；禁止 2015 年后术语（抖音、共享单车、5G、健康码、微信支付以外的表述等，具体清单见第 8 节）。

## 6. 五屏 UI 与 ReactBits 组件映射

平台约束（2026-11-22 用户确认）：**只做移动端竖屏 UI**。设计基准 375-430px 宽，单列布局；桌面浏览器中显示为居中的 430px 手机列，不做桌面多栏布局。触控热区 ≥44×44pt；底部操作固定在拇指区；不使用依赖 hover 才能触发的交互。

全局常驻：Silk（背景）+ Noise（颗粒）+ GradualBlur（边缘渐隐），每屏常驻效果 ≤3、每路由 WebGL 主背景 ≤1。

| 叙事主界面 | 顶部地点时间条与三值 HUD；中部独立滚动的阅读区；下部固定的选项/继续区（两区分离，选项不覆盖正文）；选项在阅读区滚动到正文底部后才出现 | TextType 打字机（blur、bar 光标、onSentenceComplete 解锁选项）、RichText 人名高亮（颜色加粗、点击弹出人物卡）、StarBorder 选项卡（as=button、仅 A/B/C 徽标与文案，不显示任何倾向/风险/属性）、SpotlightCard 可选线索提示、LocationBar/StatMeters 原生 |

## 7. UI/UX 规范（.wiki 提炼）

- 可发现性：每屏 3 秒回答「我在哪、什么时间、我能做什么」；地点条常驻真实区名与地点名。
- 前馈与反馈：选项不显示数值、倾向或风险标签，玩家只凭剧情文案判断（2026-11-22 用户确认）；选择后 150ms 内反馈线索入档与数值微飘字；结局页回放关键分歧。
- 正文人物：出场人物姓名以主题色加粗（冷青色，无下划线），点击弹出人物简介卡（角色、身份、一句话背景），不打断阅读、不离开当前场景。
- 防剧透：人物简介只写公开身份与表面印象，禁止出现秘密、凶手身份、死亡结局与阵营反转；档案库人物页只显示已在正文中出场过的角色（按正文扫描记录，随进度解锁）。
- 撤销优于确认：普通选择 3-5 秒可撤销；只有覆盖/清除存档用 HoldButton 长按确认。
- 防误触：选项卡整行可点、最小高度 48px、间距 8-12px、点击后 150ms 输入缓冲。
- 外部记忆：线索板、人物卡、章节摘要常驻可查；新线索高亮「新增」。
- 组块：每屏最多 4 个主操作；线索按人物/地点/时间/物证分组，每组不超过 5 条。
- 排版：正文 18px、行高 1.8、行宽 640-760px（32-40 汉字）、左对齐、段首不缩进；标题用衬线（Songti SC/思源宋体），正文用黑体栈（PingFang SC/思源黑体/Microsoft YaHei），字体栈必须含中文回退；数字 tabular-nums；字号令牌 calc(Npx * var(--fs-scale)) 单点缩放。
- 色彩：暗色表面 L0-L4 明度阶梯（背景 #0A0E13 级、非纯黑）；正文对比度 ≥4.5:1、大字 ≥3:1；饱和度预算 90-8-2；语义色固定（线索琥珀、记忆灰紫、危险猩红、成功低饱和绿）；颜色不单独承载信息。
- 布局：单列垂直流（地点时间 → 正文 → 选项）；阅读区与选项区分离，阅读区独立滚动、选项区固定在下方且不覆盖正文；抽屉从右滑入退回右侧 180ms；移动端全部单列，触控热区 ≥44×44pt。
- 键盘：A/B/C 或 1/2/3 选择，方向键移动，Enter 确认，Esc 暂停/返回，Space 跳过打字，焦点环 2px 且与 hover 同等明显，模态焦点陷阱与归还。
- 报错：显示「发生什么+为何+如何解决」，不出现内部 id 与异常栈。

## 8. 内容规范

- 视角：正文第二人称「你」（江嘉视角）；闪回碎片为第二人称现在时短句；选项用动宾结构一句话（≤40 字），不加句末冒号。
- 引号：对话用「」，不用“”；正文单段不换行，避免数据转义问题。
- 长度：普通场景正文 300-600 字；章节开场与结局可到 800 字；选项文案 15-40 字。
- 禁止：现代网络流行语、2015 年后事物（抖音、共享单车、5G、健康码、直播带货等）、真实警员姓名、真实未公开地址、露骨的作案手法与性暴力描写（侧写/留白/法律术语）。
- 真实地理：只用 hz-locations.json 白名单内的地点；2015 年区划与地铁事实固定（见改编设计第 4 节）；机构（学校/医院/公司/会展/会所）一律虚构名。
- 每章必须有：一处杭州地标作为空间锚点、一条主线线索推进、一个可错过的支线细节、一个记忆碎片或记忆触发点。
- 文风：冷峻克制，江南潮湿感，短句为主；禁止感叹号滥用；刑侦程序用语准确。

## 9. 动效方案

- 节奏令牌：按下 80ms（scale 0.97）；hover/界面缓动 120ms cubic-bezier(0.2,0,0,1)；入场 200-240ms；章节转场 480-700ms；核心数据 150ms 内渲染。
- 页面转场：路由切换 220ms 淡入+8px 上移；前进后退方向相反；章节边界 PixelTransition dither 擦入，可点击跳过。
- 打字机：TextType，速度四档（慢 45ms/字、标准 28ms/字、快 14ms/字、瞬显 0）；点击正文或 Space 立即补全；onSentenceComplete 解锁选项。
- 选项入场：打字完成后 3 张卡 stagger 50ms、240ms 上移淡入；键盘随时可用。
- 记忆闪回：GlitchText（intensity 0.35、600ms）+ PixelTransition + DarkVeil，全流程 ≤3 次。
- 结局：HoloCard 翻面 → SplitText 标题 → BlurText 正文 → CountUp 统计 → 分歧回放 stagger；全程可跳过。
- 性能：只动画 transform/opacity；prefers-reduced-motion 与设置开关双降级（背景 paused、转场直切、打字机瞬显、Glitch 关闭、CountUp 直接显示终值）。

## 10. 剧本规模与生产流程

- 结构：序章 + 7 章，23 个分支点（每点 3 选项 = 69 条选项文案），约 60-70 个场景节点。
- 预算：正文 3.5-5 万字，选项与系统文案约 0.5 万字；结局 3 篇各 800-1200 字；尾声变体 2 段。
- 生产流程：按《改编设计》章节表 → 每章先写节点大纲与分支效果（数据先行）→ 再写场景正文 → 最后过内容规范检查（真实地名、2015 术语、禁用词、长度）。
- 数据先行：任何文案进入正文前，其场景 id、选项 effects、next 必须先在章节 JSON 中定稿并通过 story-data.test.ts。
- 分支汇流：同章内的分支选项汇回同一后续场景，用 flag 决定该场景的文本变体与可选线索；不写 3 的 N 次方条独立剧情。

## 12. 风险

- 文案量大：用「数据先行 + 分支汇流」控制；每章完成即校验，避免返工。
- 好结局可达性：靠固定保底线索 + 模拟测试双重保证。
- WebGL 性能与上下文：每路由 1 个主背景；结局页 HoloCard 与背景二选一；移动端 dpr ≤1.5。
- 中文分词：BlurText 必须 letters；DecryptedText 传中文字符集；TextType 无 skip 需容器自建。
- 内容合规：真实地理 + 虚构机构 + 敏感内容留白 + 虚构声明。
- 存档损坏：版本迁移 + 快照 + 备份恢复。
- 原著改编接受度：开场声明「平行改编」，主线真相忠于原著。
